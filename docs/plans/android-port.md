# Android port

Branch: `feat/android`, worktree `../TargetX-android`, cut from `main` at `949cc36`

## What this is

TargetX on a phone. Same Rust core, same Solid frontend, same KTU engine, in a
Tauri Android shell — distributed as a downloadable APK.

Full sync parity: the port keeps etlab login, attendance, marks and the
day-by-day record. Mobile is the same app on a smaller screen, not a reduced
companion. That follows the 0.4.0 promise in the README — *nothing is taken
away from you*.

## Why Android only

iOS is not a code decision, it is a platform gate, and it is worth writing down
so the question does not get reopened every few months.

Apple permits no downloadable-install path. Outside the EU there is no
sideloading, so "download the IPA" installs nothing for an ordinary student.
Reaching an iPhone requires all three of: a Mac or macOS CI runner to build,
an Apple Developer Program membership at $99/yr, and distribution through
TestFlight or the App Store. Xcode does not run on Windows, so the development
machine cannot produce an iOS build at all.

This is not a Tauri limitation. Flutter, React Native, Kotlin Multiplatform and
plain Swift hit the identical wall — `flutter build ipa` needs Xcode exactly as
Tauri does. Rewriting the app in another framework would cost the entire Solid
UI and the entire Rust core and still leave the gate shut.

So: Android now. iOS becomes possible later at the cost of a funded Apple
account plus a macOS runner, on top of port work that is ~90% shared. Nothing
in this design forecloses it.

## Toolchain

Pinned, with reasons. All of this was already on the machine except the Rust
targets.

| Piece | Version | Why this one |
|---|---|---|
| Android SDK | compileSdk/targetSdk 36 | Tauri's generated default |
| minSdk | 24 (Android 7.0) | Tauri's floor. Kept rather than raised: cheap and older handsets are common in the target audience, and nothing in the port needs newer APIs — Keystore needs only 23 |
| NDK | **28.2.13676358** | **Not 27.** Google requires 16 KB memory-page alignment for new Play submissions; only NDK 28+ emits compliant binaries. Building on 27 yields an APK that sideloads fine and gets rejected by Play |
| JDK | Android Studio's bundled **JBR 21** | The machine's default `JAVA_HOME` is Temurin **25**, which Gradle/AGP do not support. This is the first mystery failure anyone reproducing this build will hit |
| Rust targets | `aarch64-linux-android`, `armv7-linux-androideabi`, `i686-linux-android`, `x86_64-linux-android` | installed via `rustup target add` |

Environment for any Android command:

```sh
export ANDROID_HOME="$LOCALAPPDATA/Android/Sdk"
export NDK_HOME="$ANDROID_HOME/ndk/28.2.13676358"
export JAVA_HOME="/c/Program Files/Android/Android Studio/jbr"
```

### Gradle 8.14, not the generated 8.14.3

`tauri android init` pins the wrapper to `gradle-8.14.3-bin`. That is changed
to `gradle-8.14-all`, which is a deliberate deviation and not a local hack.

The 8.14.3 distribution is 137 MB and this machine pulls it from GitHub's
release-assets CDN at roughly 95 KB/s — about 24 minutes. The Gradle wrapper's
own connect timeout expires long before that, so `tauri android build` fails
with `java.net.SocketTimeoutException: Connect timed out` and leaves a
zero-byte `.part` behind, which the next run then trips over. Two builds died
this way before the cause was clear; the error names Gradle's downloader, not
the network, so it reads like a build fault.

8.14 was already fully cached locally (`.ok` marker present), so the wrapper
resolves it without touching the network at all. AGP 8.11.0 — what the
generated project uses — requires Gradle 8.13 or newer, so 8.14 clears the
floor, and 8.14 to 8.14.3 is a patch difference with nothing relevant in it.

Anyone building elsewhere is unaffected: the URL is a normal published Gradle
distribution and downloads the usual way. Revert the pin to 8.14.3 whenever
someone has the bandwidth to fetch it.

### The generated project is committed

`app/src-tauri/gen/android/` is generated by `tauri android init` and **is
committed**. Tauri's guidance is to gitignore it only when it stays untouched;
this port adds Kotlin to it for the Keystore backend, so it is source.

## What ports unchanged

Most of the app. Worth stating explicitly, because it is the reason this is a
port and not a rewrite.

- The whole Rust core — `etlab.rs`, `ktu.rs`, `oauth.rs` — compiles for
  `aarch64-linux-android` without modification. `reqwest` with `rustls-tls`
  was chosen originally so the TLS stack would not differ between machines;
  that choice pays again here, because there is no system-TLS variation to
  absorb.
- The entire `engine/` — targets, CIE, attendance, grades, day-wise. Platform
  independent by construction.
- Persistence. `persist.ts` writes `state.json` under `appDataDir()` through
  the fs plugin, which resolves to app-private storage on Android. `hasFileStore()`
  already keys off `__TAURI_INTERNALS__` and is correct as written.
- Sync detection. `canSync()` keys off the same thing and is correct.

## Parity: every screen ships

The mobile build is the desktop app on a smaller screen. No screen, panel or
control is dropped, and no feature is desktop-only. Where a layout cannot
survive 360 px it is **re-laid out**, never removed.

The one exception is `WindowChrome` — minimise, maximise, close and the drag
region. That is not a feature being cut; it is the replacement for an OS title
bar, and Android has no window for it to control.

## What has to change

### 1. The shell

`decorations: false` plus a hand-built title bar is a desktop construct.
`WindowChrome` renders minimise/maximise/close, and `hasOwnChrome()` returns
true whenever `__TAURI_INTERNALS__` exists — which includes Android. Left
alone it would paint window buttons on a phone.

- `hasOwnChrome()` gains a platform check so it is false on Android.
- `data-tauri-drag-region` is inert on mobile; harmless, left in place.
- The header cannot hold home + four tabs + Ask + semester pills + window
  buttons at 360 px. Navigation moves to a **bottom tab bar** on mobile
  (Ledger, Attendance, Home, Tex), which also puts the targets within thumb
  reach. The header keeps the semester pills and Ask.
- `minWidth: 1100` / `minHeight: 640` are desktop window constraints and do
  not apply to the Android window; the desktop config is untouched.

### 2. The Ledger — target-led cards

The core screen, and the first of the two that genuinely do not fit. It is a
14-column table (Code, Course, Cr, CIE, Attendance, ESE, Total, Gr, Pass,
Target, Need, Status, +2) plus a side Drawer. At 360 px the course name and
the `Need` figure are nine columns apart and never on screen together, which
defeats the point of the app.

On mobile it becomes **one card per subject**:

- Headline is **the ESE mark still needed**, large, in status colour, with
  "for your target of A" beside it. This is the number the product exists to
  compute; on desktop it is column 11.
- Beneath it a thin strip: CIE, attendance, mark-to-pass.
- Attendance — and only attendance — carries a hairline bar, because it is the
  one figure that genuinely is a percentage. Rejected the alternative of
  drawing every stat as a bar: rendering "need 49/60" as an 82%-full bar
  encodes a required threshold as though it were progress, and reads as
  "nearly there" when the truth is the opposite.
- Tap expands the card into the detail rows (attendance CIE earned, series and
  assignment, resulting grade, classes still missable) and the edit controls.

The Drawer's analytics do not fit beside a card list, so on mobile the Drawer
becomes a sheet opened from the Ledger rather than a panel sitting permanently
beside it. Every chart and figure it currently shows is kept — it changes
where it lives, not what it contains.

### 3. Attendance — the timetable

The second screen that genuinely does not fit, and the less obvious one.

`calendar.css:108` sets `min-width: 820px` on the timetable grid, with day
columns pinned at `width: 14ch` / `min-width: 14ch`. The existing comment
explains why, and it is a real constraint rather than an oversight: below that
width eight periods stop being legible and course names run one line into the
next. A phone is 360 px. Squeezing it would produce exactly the illegibility
the comment was written to prevent.

So the week grid is re-laid out rather than scaled:

- **One day per screen**, with the week as a swipeable strip of date pills
  across the top and the selected day's periods listed vertically beneath.
  A period gets a full-width row, so a course name has the room the desktop
  grid gives it and the legibility constraint is satisfied instead of broken.
- The month/day-wise record keeps its calendar shape — a 7-column month grid
  is naturally square and survives 360 px, since each cell is a dot and a
  number rather than text.
- Everything the screen currently reports is kept: what can still be missed,
  what it is costing in CIE marks, the per-subject breakdown, and the
  day-by-day record.

### 4. Credentials — Android Keystore

`creds.rs` stores the portal login in the OS vault, opt-in, and is currently
`#[cfg(windows)]` (DPAPI via Credential Manager). Every other platform compiles
a no-op backend, so "remember my password" silently stores nothing.

On desktop that is a mild annoyance. On Android it is the whole experience: the
portal password gets retyped on a phone keyboard before every sync, making the
app's core loop — sync, check, sync again — its worst part.

So `creds.rs` gains a third `#[cfg]` arm backed by the Android Keystore
(`EncryptedSharedPreferences`), reached over JNI. The file already has the
backend seam; this fills in a platform rather than redesigning anything.

The security promise is unchanged and stays literally true: opt-in, stored in
the operating system's own vault, never in `state.json`, never in the export,
never in a log. Windows says DPAPI, Android says Keystore.

Biometric unlock (`androidx.biometric`) is **not** in scope. It sits on top of
this layer and can be added later without touching it; building it now means a
dependency and a no-sensor fallback path for something nobody has asked for.

### 5. Updates — the real gap

There is no Tauri updater on Android; `lib.rs` already registers the updater
and process plugins under `#[cfg(desktop)]` for that reason.

The consequence is easy to miss. `canUpdate()` returns true on Android, because
it only tests for `__TAURI_INTERNALS__`. The plugin is not registered, so
`check()` throws, the fail-silent path swallows it, and a student is never told
a new version exists. They sit on an old build forever.

That matters more here than in most apps, for the reason `update.ts` already
states: the engine IS the product, a build with a marks bug reports a wrong
number with the same confidence as a right one, and `curriculum.json` refreshes
from the repo at runtime — so an old binary keeps pulling new data while the
code reading it stands still. An APK that cannot tell you it is stale is the
worst version of that problem.

**Approach: an in-app version check, no store required.** On Android,
`update.ts` checks the published release feed directly instead of calling the
plugin, and on finding a newer version shows the existing update notice —
except that the action opens the release page in the student's browser to
download the new APK, rather than installing in place. `opener` is already
shipped and already scoped to this project's own GitHub URLs.

Rejected: **Google Play**. It is genuinely cheap ($25 once, versus Apple's
$99/yr) and would give real auto-updates. Set aside for now because a new
personal developer account must run a closed test with 12 testers for 14 days
before it may publish to production, and because an app that signs into a
college portal with a student's password is a policy question that should not
sit on the critical path of a first release. Worth revisiting once the APK is
proven — the design does not preclude it.

Requires a CSP change: `connect-src` currently allows `raw.githubusercontent.com`
and the ask worker. The release feed lives on `github.com`, so that origin must
be added for the Android build.

## Coordination with `scheme-profiles`

Session `targetx-70` is concurrently lifting the hardcoded KTU 2024 constants
out of `engine/constants.ts` into a named, editable scheme profile, so
autonomous-college students can set their own.

That directly affects this port, and the mobile card must be built for it from
the start rather than retrofitted:

- Grade labels ("target of **A**") come from the profile, not a literal.
- The attendance bands and their colours (85/80/75/70/60) are profile values.
- ESE denominators (`/60` vs `/40`) follow the course type, which is a profile
  value.

So the mobile Ledger reads all of these from the scheme rather than baking in
KTU 2024. When the shim lands, the mobile view should need little or no change.

File ownership, agreed between sessions:

| Owner | Paths |
|---|---|
| `targetx-70` | all of `app/src/engine/`, `README.md`, `docs/index.html`, `app/src/ui/Setup.tsx` |
| this port | `app/src/ui/Ledger.tsx`, `app/src-tauri/gen/android/`, `creds.rs`, mobile styles |

No state-schema collision: this port adds no persisted state. Credentials go to
the Keystore, never to `state.json`, so `targetx-70` owns the schema and its
migration alone.

## To verify on the emulator

Claims this design rests on that have not been tested yet. A `Pixel_7` AVD is
available.

1. **Cleartext portals.** The generated release config sets
   `usesCleartextTraffic = "false"`, and many college etlab instances are
   HTTP-only (`etlab.rs:51` explicitly handles `http://`, and the base URL is
   student-supplied). Android's cleartext policy governs its own networking
   stack — WebView, OkHttp — and Rust's `reqwest` opens its own sockets, so it
   *should* be unaffected. This must be confirmed against a real HTTP portal
   before release, not assumed. If wrong, it blocks a large share of users.
2. That an etlab login completes end to end on-device.
3. That `state.json` survives an app restart and an update-in-place.
4. That the Keystore entry survives a restart and is gone after uninstall.
5. Card layout at 360 px, and at 320 px (the narrowest phone still in use).
